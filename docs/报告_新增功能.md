## 一、计组部分：溢出检测改进

### 1.1 改进前的问题

Lab1 的组合逻辑 ALU 用一根 `overflow` 输出线表示溢出，只有在**当拍**才能取到它的值：

* **判据单一**：只对 `ADD`/`SUB` 做有符号判定 `(a[31]==b[31]) && (s[31]!=a[31])`；乘、除没有溢出概念；
* **没有"记忆"**：流水线里 EX 级那一拍的 `overflow`，到 WB 级、到程序后面就再也拿不到了；
* **不能统计**：测试程序无法回答"这段程序一共溢出了几次"；
* **上板不可见**：没有内存映射出口，软件读不到，也没法在数码管/串口上演示。

### 1.2 改进方法（把 Lab1 的标志位做法迁进流水线）

**① 新增标志寄存器 `FlagReg.v`**，在每条算术类指令于 EX 级退役的那一拍整体锁存：

```
flags[7:0]（映射到 0x1000_0300 CPU_FLAGS）
  [0] SF        结果符号位
  [1] ZF        结果为零
  [2] CF        加法进位 / 减法借位
  [3] OF        最近一次算术运算是否溢出
  [4] OF_STICKY 粘滞溢出位：溢出过就保持 1，直到 clrflags
  [5] PF        结果偶校验（~^result）
  [6] SEEN      复位后是否已执行过算术类指令
  [7] 保留 0
of_count[31:0]  溢出累计次数（映射到 0x1000_0304 OF_COUNT）
```

相比 Lab1 的三点增强：**粘滞溢出位 OF_STICKY**、**溢出计数器 of_count**、
**只有算术类指令才刷新标志**（见 ③）。

**② 每种运算各自给出溢出判据**，在 EX 级算好再写进 `FlagReg`：

| 运算 | 溢出判据 | 实现位置 |
|------|----------|----------|
| `ADD` / `ADDI` | `(a[31]==b[31]) && (res[31]!=a[31])`（同号相加、结果变号） | `ALU.v` |
| `SUB` | `(a[31]!=b[31]) && (res[31]!=a[31])`（异号相减、结果变号） | `ALU.v` |
| `MUL`/`MULH` 等 | 64 位积的高 32 位不是低 32 位的符号扩展：`mul_ss[63:32] != {32{mul_ss[31]}}` | `ALU.v` |
| `DIV`/`DIVU`/`REM`/`REMU` | `div0`（除零）或 `INT_MIN / -1`；结果按 RISC-V 语义给（商 = -1 / INT_MIN，余 = 被除数 / 0） | `DivUnit.v` 的 `div_of` |

> 乘除法是本次一并加入的 **M 扩展**（`MUL/MULH/MULHU/MULHSU/DIV/DIVU/REM/REMU`，
> opcode `0110011` + `funct7=0000001`，由 `ControlUnit.v` 译码成 `is_mul`/`is_div` 等），
> 溢出检测顺带覆盖了它们：`ex_of = is_div ? div_of : alu_overflow`。

**③ 门控**：`upd_flags` 只对算术类指令（`ADD/SUB/ADDI/MUL*/DIV*/REM*`）有效；
逻辑、移位、访存、跳转、`auipc` 等指令**不刷新**标志 —— 否则一条 `lw`/`sw` 就会把刚算出来的
`OF` 冲掉，测试程序根本读不到。

**④ 两种读取/清除方式**：

* **自定义指令**：`rdflags rd`（`custom-0` opcode `0001011`，`funct3=001`）把 `flags` 读进 `rd`；
  `clrflags`（`funct3=000`）清零 `flags` 与 `of_count`；
* **内存映射**：`0x1000_0300 CPU_FLAGS`（低 8 位镜像）、`0x1000_0304 OF_COUNT`（32 位计数），
  由 `PeriphMMIO.v` 暴露，软件用 `lw` 就能读。

**⑤ 多周期除法与标志的配合**：`DIV/REM` 采用移位相减，需要 32 拍。EX 级插入 `stall`
（`div_busy` 期间冻结 PC/IF-ID/ID-EX、给 EX/MEM 注气泡），只有在收尾那拍 `done` 有效时
才写 `rd` 与标志 —— 保证"标志值 = 这条除法指令的结果"，而不是中间态。

## 二、汇编部分：蓝牙接口

### 2.1 硬件连接与控制脚

开发板上的 BLE 透传模块（CC41-A 一类）与 FPGA 之间只有两根串口线，
但模块**能不能工作取决于另外 5 根控制脚**（官方 lab08 的 `bluetooth.xdc`）：

| 信号 | 引脚 | 含义 | 工作电平 |
|------|------|------|----------|
| `bt_txd` / `bt_rxd` | N2 / L3 | FPGA→模块 / 模块→FPGA（UART, **9600** 8N1） | — |
| `bt_pw_on` | D18 | 模块电源开关 | 1 = 上电 |
| `bt_rst_n` | M2 | 模块复位（低有效） | 需先拉低再释放 |
| `bt_master_slave` | C16 | 主/从模式选择 | 1 = 从机（手机连它） |
| `bt_sw_hw` | H15 | 软/硬串口选择 | 0 |
| `bt_sw` | E18 | 模式开关量 | 1 |

FPGA 侧用**一对和 USB-UART 完全相同**的 `UartChannel`（`UART_TX` + `UART_RX`），
只是波特率分频参数不同：

```verilog
parameter integer BAUD_DIV    = 434,   // USB-UART 115200 @50MHz
parameter integer BAUD_DIV_BT = 5208,  // 蓝牙   9600   @50MHz
```

### 2.2 新增的 MMIO 寄存器（`PeriphMMIO.v`）

| 地址 | 名称 | 访问 | 说明 |
|------|------|------|------|
| `0x1000_0010` | `BT_DATA` | w/r | 写：发送一个字节；读：最近收到的字节（读后自动清 RX_READY） |
| `0x1000_0014` | `BT_STATUS` | r | bit0 `TX_BUSY`，bit1 `RX_READY` |
| `0x1000_0018` | `BT_CTRL` | w | bit0 `pw_on` / bit1 `master_slave` / bit2 `sw_hw` / bit3 `sw` / bit4 `rst_n`；**复位值 0x1B** |

CPU 侧看蓝牙和 USB-UART 的寄存器用法完全一样（只是地址不同），
所以同一个"轮询 `STATUS` → 读写 `DATA`"的通信框架可以复用。

### 2.3 调试过程中遇到的问题与解决

1. **模块完全没反应（不上电 / 一直被复位）**
   手册只画了 TX/RX，漏掉了 5 根控制脚。核对官方 lab08 的 `bluetooth.xdc` 后补上，
   并加 `BT_CTRL` 寄存器；程序启动时先把 `bt_rst_n` 拉低保持 **20 ms**，再写 `0x1B`
   释放复位（`0x1B = pw_on=1, master=1, sw_hw=0, sw=1, rst_n=1`）。
2. **不确定哪种模式组合是对的** → 写 `btcfg` 扫描程序：把 5 位控制字的 32 种组合
   逐一写进 `BT_CTRL`，同时发一条 `AT` 并读回模块应答，把当前组合与结果一起显示在
   数码管上；实测只有 **`0x1B`（从模式）** 会收到 `OK`，之后手机也能正常连接。
3. **AT 指令会打断手机连接**：早期程序用 `AT`、`AT+NAME?` 等做探针，手机刚连上就被
   命令踢掉。最终演示程序**一条 AT 都不发**，只在开头做上电+复位，之后纯透传。

### 2.4 最终演示程序（btseg：手机字符 → 数码管）

程序 `Lab2.file/bt_seg.hex`（由 `gen_uart_demo.py btseg` 生成），流程：

1. 上电 → `bt_rst_n` 低电平 20 ms → 写 `BT_CTRL = 0x1B`；
2. 主循环轮询 `BT_STATUS`，等 `RX_READY`；
3. 收到一个字节后：**原样回显**给手机（串口助手能看到 `RX=<char>`），
   同时把字节写进 8 位数码管（十六进制，最新字符在最右侧并点亮小数点，实现滚动显示）；
4. 循环往复。

演示步骤：手机用任意 BLE 串口 App 连接模块 → 发送字符 → 板上数码管立即刷新，
手机同时收到回显。bitstream：`bitstream/EES338Top_btseg.bit`。

| testbench（`sim_1/new/periph/`） | 检查内容 |
|----------------------------------|----------|
| `tb_EES338_bt.v` | 模拟蓝牙模块回字节：CPU 收字节 → 回显字节一致 + `BT_STATUS` 握手 |
| `tb_EES338_btcheck.v` | 上电/复位时序（`BT_CTRL` 写 0x1B 前后 `bt_rst_n` 的 20 ms 脉冲） |

## 三、封装 IP 核

### 3.1 为什么要封装

`EES338_Core.v`（五级流水线 RV32I CPU + UART/蓝牙/LCD/数码管外设）之前只是工程里的一堆 `.v`，
对 Vivado 来说只是"源码"。**封装（Component Packaging）**要把它变成 IP 目录（IP Catalog）里
可以复用、可以在 Block Design（IP Integrator）里直接拖拽例化的"黑盒"。

### 3.2 做了什么（`scripts/package_ip.tcl`）

把 HDL 模块变成 IP，需要补四类元数据，最终全部写进 **`component.xml`**（这个文件 + 源码目录就是"IP 核"）：

| # | 元数据 | 本设计取值 |
|---|--------|------------|
| ① | 身份 **VLNV** | `ees338.bjut:ip:EES338_Core:1.0`；display name = *EES338 RISC-V 5-stage CPU + UART/BLE/LCD SoC* |
| ② | **文件组** | RTL：`EES338_Core.v` + 外设（`PeriphMMIO/UartChannel/UART_TX/UART_RX/LCD128128/SegDisplay/SimpleTimer`）+ CPU 全部子模块（`PipelineCPU/ALU/ControlUnit/FlagReg/DivUnit/RegisterFile/PC/ImmediateGenerator/InstructionMemory/DataMemory`）；头文件：`macro.vh` / `imem_boot_init.vh` / `dmem_boot_init.vh`（综合时才 `include`，必须一起打包，否则 IP 单独综合会报 `module not found`） |
| ③ | **参数** | HDL 参数（`HEX_FILE`/`DATA_FILE` 等）暴露到 IP 定制界面，并用 `ipx::infer_user_parameter_order` 排好顺序 |
| ④ | **接口** | `CLK`（`xilinx.com:signal:clock:1.0`，50 MHz）+ `RST`（`signal:reset:1.0`，`ACTIVE_HIGH`）→ Block Design 能自动连线；同时删掉打包器误判出来的 `lcd_rst_n` 复位接口（它其实是送给 LCD 屏的输出） |

脚本流程（幂等、可重复执行）：

```
建只含 IP 源文件的临时工程
  → ipx::package_project -import_files（把源文件复制进 ip_repo/EES338_Core/src）
  → 设置 VLNV / display_name / description / 文件组 / 参数 / CLK+RST 接口
  → ipx::create_xgui_files + ipx::update_checksums + ipx::save_core
  → 把 ip_repo 挂回主工程（set_property ip_repo_paths + update_ip_catalog -rebuild）
  → 校验 IP 在 Catalog 中可见（NAME == EES338_Core）
```

产物：

```
ip_repo/EES338_Core/
├── component.xml        <- IP 本体（VLNV / 文件组 / 参数 / 接口定义）
├── xgui/                <- 定制界面描述
└── src/                 <- 21 个源文件副本（-import_files 自动收集）
```

**设计取舍**：IP 内部**不含 MMCM**（时钟由外部 `clk_wiz` 提供），
这样在 Block Design 里可以自由选择/更换时钟源，也不必给 IP 加时钟约束。
